# Demo cache binding for the common screenshot/frames flow (T-16B)

Binds the reviewed demo cache (`lib/demoCache.ts`, T-16A) into the SAME `ImageDraftFlow` controller used by `/post`, as an explicit opt-in replay. Everything below is verified only by synthetic in-memory tests. **There are no genuine cache fixtures in this repository**, so no real hit has ever happened. Genuine capture, key-removed acceptance and phone/browser acceptance are PENDING. No provider call, fixture publication or backend/cloud change was made. `/reels` (the live video path) is untouched.

## Behavior
- **Opt-in only.** `FlowSnapshot.demoReplay` starts `false`, is never persisted and is never turned on by the code. The page shows a checkbox ("Replay a saved demo capture instead of calling the live service"). Nothing is fetched while it is off.
- **When it runs.** Only when the user asks for analysis with replay on AND the optional deps `demoPromptVersion` + `loadDemo` exist (old callers/tests without them are unchanged). The real uploads happen first, so every published image still has a real owned receipt from the authenticated upload route; the cache never supplies receipts, storage ids, profile, location or confirmation.
- **Lookup.** Key = `demoKey` over: the exact original picked file bytes; ALL prepared uploaded images (bytes hash + MIME, in upload order); the trimmed caption/text/provenance link/publication date exactly as the live call would send them; and the prompt/contract version. `loadDemoFixture` fetches `/fixtures/demo/<original-sha256>.json` (same origin, 2 MB cap, 3 s own deadline); the controller adds an outer 4 s deadline and an abort race so even a non-settling injected loader is bounded.
- **Hit.** The captured `ExtractOutcome` goes through the same `validateExtractOutcome` → `extractOutcomeToDrafts` as a live result, so blocking reviews (e.g. FUTURE_START) and every sidecar note survive, suggestions stay unreviewed and no location is set. The live `extract` call is skipped. The offer carries `cached: {capturedAt, evidenceReference, model}` (absent for live) and the UI labels it "Saved demo capture (cached), not a live analysis" with an honest note. Cached provenance is an operator assertion, not proof of a provider call or of fresh latency.
- **Miss / invalid / slow / error / unhashable source.** Continue to the live extraction exactly once. **Cancel** (or unmount, or picking another source) ignores a late hit AND a late miss: no extract call, no state output. Retrying re-runs the lookup against the retained key material (no re-reading, re-preparing or re-uploading); editing the context changes the key. Manual form edits are never touched; applying an offer over an edited form still needs confirmation.
- **Recording.** Matches only the original recording file plus exactly four actual frames in upload order (a different frame or order is a miss). Offers say "4 frames... no audio or video was analyzed"; no frame is attached as the deal photo.
- **Receipt material.** The source receipt keeps only SHA-256 hashes and MIMEs of the original and prepared bytes (bounded, tiny). Original files over 20 MB, prepared images over 5 MB or unreadable sources simply have no cache.
- **Server key absent.** A hit works without the Gemini key because extraction is skipped; a miss shows the normal live failure (e.g. CONFIGURATION). Uploads still need the real authenticated upload route.

## Prompt/contract version
`currentPromptVersion()` = `extract-outcome-v1:` + first 24 hex of SHA-256 over `[SYSTEM_PROMPT, RESPONSE_JSON_SCHEMA, buildContextText({imageCount:0}), "extract-outcome-v1"]` from `lib/prompt.ts`. Editing the prompt, schema or context builder changes it, so every older capture becomes a miss. Bump `EXTRACT_ENVELOPE_CONTRACT` when the outcome envelope shape changes. (Not covered: server-only request assembly in `lib/extractCore.ts` and the model id; the capture records the model in its provenance. Re-capture after any such change.)

## Capture and copy protocol (instructions only; nothing was run)
1. Operator, with an authorized live Gemini key and replay OFF, runs the real flow on the actual demo image (or recording) with the exact caption/text/link/date to be used on stage. Keep a redacted local run log as the evidence reference.
2. Obtain the actual prepared upload bytes: the controller uploads exactly the resized JPEG(s) it hashes; download them from the authorized owned storage while they exist (or save the browser-prepared Blob during the capture run). For a recording, use the four uploaded frames in upload order.
3. Compute the key with a local script using `demoKey({ original, images, caption, text, provenanceUrl, publishedAt, promptVersion: await currentPromptVersion() })` (original = the exact file picked; trimmed context identical to what was submitted).
4. Write `fixtures/demo/<sourceSha256>.json` as `{version:1, sourceSha256, requestSha256, promptVersion, provenance:{kind:"live-provider-capture", capturedAt, evidenceReference, model}, outcome:<the full ExtractOutcome envelope, unmodified>}`. Never save a bare result, a hand-written outcome, a key or a token.
5. Northstar reviews the run evidence. Only then copy approved files to `public/fixtures/demo/` (same-origin static); this ticket does not do that.
6. Acceptance (pending): with the Gemini key removed from the deployment and replay ON, the same inputs produce a cached offer; any change to image, context, frame order or prompt produces the normal live path.
